# N64 and 3DS

TwinPlay already emulates DS, GBA, GB, GBC, NES and Super NES. This branch adds N64 and 3DS
by embedding existing cores. It does not include a new CPU or GPU written for this app, and it
does not include ROMs, BIOS, firmware or keys.

The branch is `n64-3ds`, cut from `118ef02`. N64/3DS code is additive: new files under
`Core/n64/`, `Core/n3ds/`, `Core/src/N64Core.cpp`, `Core/src/N3DSCore.cpp` and
`Core/src/ConsoleImage.cpp`, plus the system enum, library extensions and on-screen controls.
DSP-1, Mode 7 and the Mario Kart harness are untouched so they can merge later.

### N64, no JIT

Delta and Provenance ship Mupen64Plus on iOS by **not using the dynarec**. This build passes
`NO_ASM=1 OSD=0 VULKAN=0` to `projects/unix/Makefile`. That makefile then omits
`new_dynarec` and the old recompiler. `R4300Emulator` is set to `1` (cached interpreter).
If a config file asks for the dynarec anyway, the `NO_ASM` binary has no dynarec objects, so
the core falls through to the cached interpreter.

The RSP is `mupen64plus-rsp-hle` (high-level, no RSP JIT). Video is GLideN64, which is what
Delta and Provenance use. It renders into an offscreen OpenGL context (`Core/n64/vidext_egl.cpp`
on desktop; `Core/n64/vidext_eagl.mm` is the iOS equivalent, an offscreen EAGL / OpenGL ES 3 FBO). Each presented
frame is read back and scaled into the existing 256×192 picture so the Metal presenter, lid and
window code stay as they are.

Audio and pad plugins in `Core/n64/` are original shims over the Mupen plugin ABI. They are
GPL-2.0-or-later because they implement that ABI. The pad exposes the N64 stick and C buttons.
Save states go through `M64CMD_STATE_SAVE` / `M64CMD_STATE_LOAD` (one emulated frame is stepped
so the core can flush the job). Cartridge SRAM/EEPROM/Flash is written by the core into the
game's save directory.

### 3DS, no JIT

Azahar 2127 adds **FastInterp**, a cached interpreter written for iOS and tvOS, where JIT is
forbidden. `use_cpu_jit` defaults to on in Azahar; a TwinPlay build must force it off and leave
`use_fastinterp` on, and it must **not link dynarmic**. Dynarmic is a JIT. The CMake hook for
that is `-DTWINPLAY_NO_JIT=ON` once the patch described below is applied. The software renderer
(`ENABLE_SOFTWARE_RENDERER`, OpenGL and Vulkan off) writes both screens into CPU buffers. Those
are letterboxed into the same 256×192 pair the DS layout already draws, so the bottom screen
stays the touch screen.

FastInterp is much faster than Citra's old interpreter. Azahar's iOS notes describe full-speed
play on an iPhone XS **with a GPU renderer**. The software renderer used here to feed TwinPlay's
existing texture will be slower. A MoltenVK/Vulkan path would be the performance follow-up; Azahar
turns OpenGL off on Apple.

On iOS, `scripts/build-n64-3ds.sh` (invoked from Xcode, or directly on a Mac with the
iPhoneOS SDK) cross-compiles real arm64 archives: Mupen64Plus with `NO_ASM=1`, RSP-HLE,
GLideN64 on OpenGL ES / EAGL, and Azahar FastInterp with `-DTWINPLAY_NO_JIT=ON` (no dynarmic,
no xbyak, no oaknut, no shader JIT). A stamp file skips a rebuild when the real libraries
are already in place. There is no JIT anywhere in the iOS binaries.

Encrypted 3DS images still need keys the user dumped themselves. Those keys are never in
the repo. Decrypted images are what Azahar can load with `ENABLE_BUILTIN_KEYBLOB=OFF`.
`scripts/patch-azahar-no-jit.sh` applies the CMake and source guards so dynarmic, xbyak and
oaknut are skipped. Do not compile `src/core/arm/dynarmic/arm_dynarmic.cpp` into an App Store binary.

## How the app sees them

`GameSystem` gains `.n64` and `.n3ds` (raw values `"n64"` and `"n3ds"`). Existing raw values
are unchanged. File types:

- N64: `.n64`, `.z64`, `.v64` (and the three byte-order magics)
- 3DS: `.3ds`, `.cci`, `.cxi` (`NCSD` / `NCCH` at offset `0x100`)

`DSCoreKind` 6 and 7 create `N64Core` and `N3DSCore`. Both implement `EmulatorCore`. N64 is one
screen. 3DS uses the DS dual-screen layout (`isSingleScreen == false`), including the bottom-screen
touch mapping (256×192 layout pixels scaled to the 320×240 touch screen). On-screen controls add
an analog stick, N64 C buttons and Z, and 3DS ZL/ZR. A controller's left stick is the analog
stick; the right stick is the C buttons (N64) or the C-stick (3DS).

Skins: `skinN64` (`n64Charcoal`, `n64Forest`) and `skinN3DS` (`n3dsPearl`, `n3dsInk`). The N64
shell reuses the console bezel. The 3DS shell reuses the DS twin shell. Lid geometry is unchanged;
only the lid colour list includes the new skins.

`NDUO_TESTER_UNLOCK` is still only a compile-time flag in `Store.swift`. It is not set in
`project.yml`. The URL scheme, app group, bundle id and the named UserDefaults keys are unchanged.

## Build

```bash
./scripts/fetch-n64-3ds.sh
./scripts/build-n64-3ds.sh
./scripts/run-core-tests.sh
```

`project.yml` runs `scripts/build-n64-3ds.sh` before the Xcode compile and links
`libtwinplay_n64.a` and `libtwinplay_3ds.a` from `Core/third_party/build`. Plugins are copied
into the app as resources when that directory exists.

Host packages: `build-essential`, `cmake`, `pkg-config`, `libsdl2-dev`, `libpng-dev`,
`zlib1g-dev`, `libzstd-dev`, `libegl1-mesa-dev`, `libgl1-mesa-dev`.

### GitHub Actions macOS runners and Xcode Cloud

- The pre-build script is `scripts/build-n64-3ds.sh`. It is not sandboxed
  (`ENABLE_USER_SCRIPT_SANDBOXING = NO`) because it runs CMake and `make`.
- When `SDKROOT` contains `iPhone`, the script currently writes **stub** archives so the
  Xcode link succeeds without an iOS cross toolchain. Replace that branch with a cross build
  before shipping N64 on device:
  - Mupen: `make -C projects/unix NO_ASM=1 OSD=0 VULKAN=0` with `CC`/`CXX` from
    `xcrun --sdk iphoneos --find clang`, `SDL_CFLAGS`/`SDL_LDLIBS` pointing at an iOS static
    SDL2, and the same for libpng and zlib. Do not pass a dynarec flag.
  - GLideN64: `-DMUPENPLUSAPI=ON -DMUPENPLUSAPI_GLIDENUI=OFF -DNO_OSD=ON`, GLES headers from
    the iOS SDK. GLideN64 detects an OpenGL ES driver at runtime (`isGLESX`).
  - Link the resulting `.a` for the active `ARCHS`. Do not copy the Linux `.so` files into
    the iOS app.
- Azahar's own `CMakeLists.txt` already has an `if (IOS)` block (deployment target 14 in
  upstream; TwinPlay is iOS 16). Configure with Qt/SDL/web/cubeb/OpenAL/Vulkan/OpenGL off,
  `ENABLE_SOFTWARE_RENDERER=ON`, `ENABLE_BUILTIN_KEYBLOB=OFF`, `ENABLE_LTO=OFF`,
  `CITRA_WARNINGS_AS_ERRORS=OFF`, and `-DTWINPLAY_NO_JIT=ON` after the dynarmic `if` in
  `externals/CMakeLists.txt` and `src/core/CMakeLists.txt` is wrapped so dynarmic is not added.
  Expect a long first build (Boost and the other bundled libraries).
- Xcode Cloud minutes: the N64 host build is a few minutes; Azahar is much longer. Cache
  `Core/third_party/build`.

## What was verified here

On Linux, without a display used for a real frame:

- `mupen64plus-core` links with `NO_ASM=1`. `nm` shows no dynarec exports. The binary's
  strings include "Cached Interpreter" and "Pure Interpreter".
- `mupen64plus-rsp-hle.so` and `mupen64plus-video-GLideN64.so` link.
- `scripts/n64-probe` (run by the build script) calls `CoreStartup`, opens a 4 KB `.z64` header,
  attaches GLideN64, the RSP, and the TwinPlay audio/input plugins, then closes the ROM.
  It does **not** emulate a commercial game. There is no ROM in the repo.
- `./scripts/run-core-tests.sh` includes the N64/3DS image tests (byte order, NCSD/NCCH magic,
  scaling, and the "core not linked" error from the stub used by the unit-test binary).

Not verified: `xcodebuild`, the iOS Simulator, EAGL, a real N64 frame, or an Azahar link.
3DS `twinplay_3ds_available()` is 0 until that link exists.
